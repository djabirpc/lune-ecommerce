# Changelog

## [2026-09-03]

### Added
- **Shipping-rate calculation** (CLAUDE.md section 15, closing the gap left in Important Decision #46): new `ShippingRate` domain entity (`Ecommerce.Domain.Shipping`) — `Wilaya` (unique index), `HomeDeliveryPrice`/`StopDeskPrice` (numeric(10,2)), `IsActive`. New `Ecommerce.Domain.Shipping.AlgerianWilayas.All` — the canonical, hardcoded list of the 58 official Algerian wilayas, used both to seed `ShippingRate` (via `HasData`, deterministic MD5-derived GUIDs) and mirrored by a new frontend constant.
- `IShippingRateService`/`ShippingRateService` (`Ecommerce.Application.Shipping`/`Ecommerce.Infrastructure.Shipping`) — deliberately separate from `IShippingProvider` (that's carrier API access; this is the merchant's own pricing). `GetAllAsync`, `UpdateAsync(wilaya, request)`, and `GetPriceAsync(wilaya, deliveryType)` — the last throws `ValidationAppException` (`400`) for an unknown or deactivated wilaya rather than silently defaulting to `0`.
- `ShippingRatesController`: admin `GET`/`PUT /api/shipping-rates/{wilaya}` (`OrderManagers` role) and a public `GET /api/shipping-rates/quote?wilaya=&deliveryType=` for storefront checkout price previews (the backend still recalculates authoritatively at order creation, CLAUDE.md section 41).
- `OrderService.CreateAsync` now resolves the real shipping rate via `IShippingRateService.GetPriceAsync` **before** `CalculatePromotionsAsync`, replacing the hardcoded `ShippingCost = 0m`. This is also what finally makes `FreeShipping` promotions have a real, visible effect at checkout.
- Migration `AddShippingRates` — creates `ShippingRates` and seeds all 58 wilayas with a uniform placeholder rate (600 DA home delivery / 400 DA stop desk) that the admin is expected to adjust to real business costs.
- `ShippingRateTests` (9 new tests, Testcontainers): the quote endpoint returns the seeded default and rejects an unknown wilaya with `400`; order creation uses the correct rate for wilaya + delivery type and rejects an unknown wilaya; an admin rate update is reflected in the next order's shipping cost; deactivating a wilaya's rate makes orders for it fail; the admin rates list requires auth and returns all 58 wilayas. `PromotionCheckoutTests` gained `FreeShippingPromotion_ZeroesOutShippingCost` (previously untestable, since shipping cost was always `0`), and all existing `Total` assertions were updated for the now-nonzero default shipping cost.
- **Frontend**: `ShippingRateDto`/`UpdateShippingRateRequest`/`ShippingQuoteDto` types, `shippingRatesApi` (`getAll`/`update`/`getQuote`), and `ALGERIAN_WILAYAS` (`lib/data/wilayas.ts`, must be kept manually in sync with the backend's `AlgerianWilayas.cs`). `CheckoutPage`'s Wilaya field changed from a free-text `<input>` to a `<select>` of the 58 wilayas (needed for exact rate-key matching, not just UX), with a live shipping-cost quote fetched on every wilaya/delivery-type change, replacing the old "Calculée à la préparation" placeholder. `OrderDetailsCard` (storefront order confirmation) now always shows a Livraison line (previously shown only inside the discount block). `/admin/shipping` gained an editable per-wilaya rates table below the existing carrier-availability list.
- **Product/category update UI**: `catalogApi.updateProduct`/`updateCategory` added to the frontend API client (the backend `PUT /api/products/{id}`/`PUT /api/categories/{id}` endpoints already existed but had no frontend caller). New `EditProductForm` component, toggled per-row on `/admin/products` alongside the existing `ProductVariantsPanel` (only one of the two panels is open at a time per row now). `CategoryQuickManager`'s single create form gained a dual-purpose edit mode: clicking a category chip repopulates the form from that category and switches its submit handler to `updateCategory`, adding an `isActive` checkbox (shown only while editing). `ProductDetailDto` gained an additive `categoryId` field so the edit form can pre-select the product's category.
- **Product photography / file storage** (CLAUDE.md section 28): new `IFileStorageService` (`Ecommerce.Application.Common`) and `LocalFileStorageService` (`Ecommerce.Infrastructure.Storage`) — writes to local disk, returns a fully-qualified absolute URL, swappable for S3/Cloudinary/Azure Blob later without touching any calling code. `POST /api/products/{id}/images` (multipart, `CatalogManagers` role, 10 MB request-size cap, validates content-type to `image/jpeg`/`image/png`/`image/webp` and size to 5 MB max), `DELETE /api/products/{id}/images/{imageId}`, `PUT /api/products/{id}/images/{imageId}/primary`. The first image uploaded for a product is automatically made primary; deleting the primary image promotes the next by `DisplayOrder`. No migration needed — `ProductImage` already existed from the original catalog work, it just had no write path. Program.cs now serves the uploads directory via `UseStaticFiles` at `/uploads`.
- `FileStorageOptions` (config section `FileStorage`, env vars `FileStorage__LocalPath`/`FileStorage__PublicBaseUrl`, root env var `BACKEND_PUBLIC_URL`) — `docker-compose.yml` gained a persistent `uploads_data` volume mounted at `/app/uploads`.
- `ProductImageTests` (6 new tests, Testcontainers): first upload auto-primary; second upload with `isPrimary: true` swaps primary; unsupported content-type returns `400`; unauthenticated upload returns `401`; deleting the primary image promotes the next; explicitly setting primary swaps the flag.
- **Frontend**: new `ProductImagesPanel` component (third per-row panel on `/admin/products`, alongside `Modifier`/`Variantes / Stock`) — thumbnail grid, file-input upload, "Définir principale"/"Supprimer" actions. `apiClient` gained `postForm` (skips the default JSON `Content-Type` header so the browser sets the multipart boundary itself). `catalogApi` gained `uploadImage`/`deleteImage`/`setPrimaryImage`. Storefront `ProductPage`/`ProductCard` needed **zero changes** — they already rendered image data correctly and just had none to render before this.
- **Staff user management** (CLAUDE.md section 25): new `IUserService`/`UserService` (`Ecommerce.Application.Users`/`Ecommerce.Infrastructure.Identity`), built on the existing `UserManager<ApplicationUser>` — no new persistence, `ApplicationUser` and roles already existed. `GET/POST /api/users`, `PUT /api/users/{id}` (new `Roles.UserManagers` = SUPER_ADMIN/ADMIN). Users can hold multiple roles at once; updates fully replace the role set (validated against `Roles.All`, unknown role names return `400`). An admin cannot deactivate their own account (`409`) — deactivation itself was already enforced at login by the pre-existing `IsActive` check on `ApplicationUser`.
- **Frontend**: real `/admin/users` (was `PagePlaceholder`) — create/edit dual-purpose form (role checkboxes, password field only on create) plus an accounts list with Modifier/Activer/Désactiver. New `lib/format/roleLabels.ts` (`ROLE_LABELS`/`ALL_ROLES`), also applied to `AdminLayout`'s header, which previously showed raw role codes (`SUPER_ADMIN`) directly in the French UI.
- **Storefront product image gallery**: `ProductPage` now shows a click-through thumbnail strip (only when a product has more than one image) instead of only ever rendering the primary photo. Pure frontend change — `ProductDetailDto.images` already carried every uploaded image, no backend/API change needed.
- **Staff password reset**: `POST /api/users/{id}/reset-password` (`UserManagers` role, admin-triggered — no self-service "forgot password" email flow, since no email-sending integration exists in this project). Uses Identity's own `GeneratePasswordResetTokenAsync`/`ResetPasswordAsync`, and additionally revokes every active `RefreshToken` row for the account so a leaked/compromised session can't keep refreshing after the reset. New `ResetPasswordRequest`/`ResetPasswordRequestValidator` (min 8 characters). Frontend: `ResetPasswordAction` component, a collapsed link per user row on `/admin/users` that expands into an inline password field.

## [2026-09-02]

### Added
- **Shipping abstraction** (CLAUDE.md sections 15–19): `Shipment`/`ShipmentTrackingEvent` domain entities (`Ecommerce.Domain.Shipping`) — `Shipment` is 1:1 with `Order` (unique index on `OrderId`), stores `Carrier` (enum: Fake/Yalidine/ZRExpress), `ProviderShipmentId`, `TrackingNumber`, and **both** `ProviderStatus` (raw) and `NormalizedStatus` (`NormalizedShippingStatus` enum matching CLAUDE.md section 18's exact list: Created/PickedUp/InTransit/AtDestination/OutForDelivery/Delivered/Failed/Refused/Returned/Cancelled/Unknown). `ShipmentTrackingEvent` is the append-only audit trail, one row per status change.
- `IShippingProvider` (`Ecommerce.Application.Shipping`): `Carrier`, `IsConfigured`, `CreateShipmentAsync`, `GetTrackingAsync`. Three registrations resolved as `IEnumerable<IShippingProvider>` and keyed by `.Carrier` in `ShippingService`.
- `FakeShippingProvider` (Infrastructure, **Singleton**, fully functional — the mandatory dev/test double from CLAUDE.md section 15): generates a tracking number on creation, then deterministically advances one step per `GetTrackingAsync` call through `Created → PickedUp → InTransit → AtDestination → OutForDelivery → Delivered`, tracked via an in-memory `ConcurrentDictionary<string, int>` keyed by `ProviderShipmentId`.
- `YalidineShippingProvider`/`ZRExpressShippingProvider` (Infrastructure): structural adapters only — every method throws `NotConfiguredAppException` (new `501 NOT_CONFIGURED` `AppException` subclass) unconditionally. No real endpoints/authentication were invented, per CLAUDE.md sections 16/17, since no official API documentation was available for either carrier; `IsConfigured` is hardcoded `false` on both regardless of whether credentials are set. `YalidineOptions`/`ZRExpressOptions` (config sections `Yalidine`/`ZRExpress`, env vars `YALIDINE_BASE_URL`/`YALIDINE_API_ID`/`YALIDINE_API_TOKEN` and `ZR_EXPRESS_BASE_URL`/`ZR_EXPRESS_API_KEY`) exist so nothing needs to change once real docs/credentials exist beyond implementing the HTTP calls.
- `IShippingService`/`ShippingService`: `CreateShipmentAsync` requires the order to be `ReadyToShip` (409 otherwise) with no existing shipment (409 otherwise), persists the `Shipment` + first tracking event, then transitions the order `ReadyToShip → Shipped` via the existing `IOrderService.ChangeStatusAsync`. `SyncTrackingAsync` re-queries the provider, records a new tracking event only on an actual status change, and — via a `NormalizedShippingStatus → OrderStatus` map — drives the order further (`OutForDelivery`/`Delivered`/`DeliveryFailed`/`Refused`/`Returned`/`Cancelled`), reusing the same `AllowedTransitions` state machine everywhere else (a resulting `ConflictAppException` is caught and swallowed so an already-manually-moved order never crashes a sync). `GetLabelAsync` returns a clearly-marked placeholder `text/plain` label for `Fake` shipments only. `GetCarrierAvailability` reports live per-carrier status.
- `ShippingSyncBackgroundService` (`BackgroundService`, CLAUDE.md section 19 — no carrier here supports webhooks): polls all non-terminal shipments every `ShippingSync:IntervalSeconds` (config default 300s), each shipment's sync failure logged and skipped rather than aborting the cycle. Gated by `ShippingSync:Enabled` (default `true`; set to `false` in `AuthWebApplicationFactory`'s test config so it never runs during `dotnet test`).
- `POST /api/orders/{id}/shipment` (`OrdersController`, `OrderManagers` role) — `{ carrier }` → `ShipmentDto`. `ShipmentsController`: `POST /api/shipments/{id}/sync`, `GET /api/shipments/{id}/label` (`text/plain`). `ShippingController`: `GET /api/shipping/carriers` → `[{ carrier, isConfigured, unavailableReason }]`.
- `OrderDetailDto` gained `shipment: ShipmentDto | null` — populated by `OrderService` reading the `Shipments` table directly (`.Include(o => o.Shipment).ThenInclude(s => s.TrackingEvents)`), always included (like `appliedPromotions`), not admin-only.
- Migration `AddShipping`.

Admin `OrderDetailPage` gained a shipping section: a carrier-select "Créer l'expédition" form when the order is `ReadyToShip` with no shipment yet, or carrier/tracking-number/status/tracking-events plus "Actualiser le suivi"/"Voir l'étiquette" buttons once one exists. Real `admin/pages/ShippingPage.tsx` (was `PagePlaceholder`) — read-only carrier-availability list.

- **`BuyXGetY` checkout-time calculation** (CLAUDE.md section 20): `OrderService.CalculatePromotionsAsync` now includes `BuyXGetY` promotions in candidate matching (previously excluded) and dispatches each line's discount through a new `ComputeItemDiscount`, which delegates to `ComputeBuyXGetYDiscount` for `BuyXGetY` and the existing `ComputeDiscount` for every other type. Bundle math, evaluated per line item only: `bundleSize = BuyQuantity + GetQuantity`, `completeBundles = item.Quantity / bundleSize` (integer division — an incomplete bundle earns nothing), `freeUnits = completeBundles * GetQuantity`, discount = `freeUnits * item.UnitPrice` (100% off the free units). 3 new `PromotionCheckoutTests`: a complete bundle (qty 3 on Buy-2-Get-1) makes 1 unit free; multiple complete bundles (qty 6) make 2 units free; an incomplete bundle (qty 2) earns no discount and produces no `AppliedPromotions` entry.

### Fixed
