# Project Context

## Project

Luna is a custom full-stack e-commerce platform for a fashion business in Algeria.

The platform is built specifically around Algerian COD (Cash On Delivery) commerce. It is NOT Shopify/WooCommerce and must remain a fully independent, custom application (see CLAUDE.md section 2).

## Current Stack

Backend:
- ASP.NET Core .NET 9 (C#)
- Entity Framework Core 9 + Npgsql (PostgreSQL)
- ASP.NET Core Identity (custom `ApplicationUser`/`ApplicationRole`, Guid keys)
- JWT Bearer authentication (access tokens via `System.IdentityModel.Tokens.Jwt`, rotating refresh tokens hashed in DB)
- FluentValidation (wired, validators exist for Auth DTOs, invoked manually from `AuthService`)
- Serilog (console sink)
- Swashbuckle/Swagger with JWT bearer scheme
- Health checks (`/health`, Npgsql check)
- Testcontainers.PostgreSql (test-only, for real-DB integration tests — requires Docker running)

Frontend:
- React 19 + TypeScript + Vite 8
- Tailwind CSS v4 (via `@tailwindcss/vite`, no separate config file)
- React Router v7 (`createBrowserRouter`)
- TanStack Query v5 (catalog reads)
- React Hook Form + Zod + `@hookform/resolvers` (checkout + order-tracking forms)
- No frontend state library beyond React Context — cart is a single `CartContext` + localStorage

Infrastructure:
- Docker + Docker Compose (postgres, backend, frontend)
- PostgreSQL 16 (alpine image)

## Current Architecture

Backend follows a 4-project modular architecture under `backend/src/`:

```text
Ecommerce.Domain          — framework-agnostic entities/constants (Entity base class, Roles, Catalog/*, Inventory/*, Orders/*, Promotions/*, Shipping/*)
Ecommerce.Application     — use cases, DTOs, validators, service interfaces (IAuthService/ITokenService/ICategoryService/IProductService/IInventoryService/IOrderService/IPromotionService/IShippingService/IShippingProvider/IMarketingService), AppException hierarchy
Ecommerce.Infrastructure  — EF Core, Identity (ApplicationUser/ApplicationRole/RefreshToken), Catalog/Inventory/Orders/Promotions/Shipping/Marketing service implementations, AppDbContext, IdentitySeeder, AddInfrastructure()
Ecommerce.Api             — controllers (Auth/Categories/Products/Inventory/Orders/Promotions/Shipments/Shipping/Marketing), Program.cs composition root, Swagger, JWT, health checks, global exception middleware
```

Auth-related namespaces worth knowing:
- `Ecommerce.Application.Auth` — `IAuthService`, `ITokenService`, `Dtos/` (LoginRequest, RefreshTokenRequest, AuthResponse, CurrentUserResponse), `Validators/`
- `Ecommerce.Application.Common.Exceptions` — `AppException` + `UnauthorizedAppException`/`ValidationAppException`/`NotFoundAppException`/`ConflictAppException`, all mapped to the `{ success, error }` shape by `Ecommerce.Api.Middleware.ExceptionHandlingExtensions.UseAppExceptionHandling()`
- `Ecommerce.Infrastructure.Identity` — `ApplicationUser`, `ApplicationRole`, `RefreshToken`, `TokenService`, `AuthService`
- `Ecommerce.Infrastructure.Persistence.IdentitySeeder` — seeds roles + optional bootstrap SUPER_ADMIN, called from `Program.cs` alongside the dev-only auto-migration

Catalog/Inventory namespaces worth knowing:
- `Ecommerce.Domain.Catalog` — `Category`, `Product`, `ProductVariant`, `ProductImage` (plain entities, no framework dependency)
- `Ecommerce.Domain.Inventory` — `InventoryRecord` (named to avoid a type-equals-namespace clash with `Ecommerce.Domain.Inventory`), `InventoryTransaction`, `InventoryTransactionType` enum (Reserve/Release/Sale/Return/Restock/Adjustment, matches CLAUDE.md section 10 exactly, stored as string in DB)
- `Ecommerce.Application.Catalog` / `Ecommerce.Application.Inventory` — `ICategoryService`/`IProductService`/`IInventoryService`, DTOs, FluentValidation validators (including a shared `SlugValidationRule.MustBeAValidSlug()` extension)
- `Ecommerce.Infrastructure.Catalog.{CategoryService,ProductService}` / `Ecommerce.Infrastructure.Inventory.InventoryService` — EF Core-backed implementations. `InventoryService` uses `ExecuteUpdateAsync` with a guard predicate in the `Where` clause (e.g. `AvailableQuantity >= quantity`) for every stock mutation — this is an atomic, race-condition-safe SQL `UPDATE ... WHERE` (no read-then-write), which is how "never allow overselling" (CLAUDE.md section 10) is actually enforced under concurrent requests. If you add new stock-mutating logic, follow this exact pattern rather than loading the entity and saving it back.
- `IProductService.GetPagedAsync` and `ICategoryService.GetAllAsync` both take an `includeInactive` flag (default `false`, preserving public storefront behavior). `GET /api/products`/`GET /api/categories` expose it as a `?includeInactive=true` query param on the **same public, `[AllowAnonymous]` endpoint** — deliberately not a separate admin-only endpoint, since which products are deactivated isn't sensitive data (unlike order/customer info), and the admin UI needs to see everything it manages, including things it has itself turned off.
- `Ecommerce.Domain.Identity.Roles.CatalogManagers` — comma-joined `SUPER_ADMIN,ADMIN,STOCK_MANAGER` constant for `[Authorize(Roles = ...)]` on catalog/inventory write endpoints

Orders namespaces worth knowing:
- `Ecommerce.Domain.Orders` — `Order`, `OrderItem` (price/name **snapshotted** at order time, never re-read from the product later), `OrderStatusHistory`, `OrderStatus`/`DeliveryType`/`PaymentStatus` enums
- `Ecommerce.Application.Orders.IOrderService` / `Ecommerce.Infrastructure.Orders.OrderService` — `CreateAsync` (validates → reserves stock for every line inside one DB transaction, all-or-nothing) and `ChangeStatusAsync` (validates the transition against a hardcoded `AllowedTransitions` map before doing anything, then applies the matching inventory side effect: `Cancelled`/`Refused` → `ReleaseAsync`, `Delivered` → `RecordSaleAsync` + `PaymentStatus = Collected`, `Returned` → `RecordReturnAsync`, everything else is a no-op on inventory)
- `Ecommerce.Domain.Identity.Roles.OrderManagers` — `SUPER_ADMIN,ADMIN,ORDER_MANAGER,CONFIRMATION_AGENT` for order admin endpoints
- Program.cs registers a global `JsonStringEnumConverter` on the MVC JSON options, so `OrderStatus`/`DeliveryType`/`PaymentStatus` (and any future API-facing enum) (de)serialize as PascalCase strings (e.g. `"PendingConfirmation"`), matching the CLAUDE.md section 45 code-naming example — **not** the SCREAMING_SNAKE_CASE used in the workflow diagram in section 12, which is diagram notation, not a literal contract. Test HTTP clients must configure a matching `JsonSerializerOptions` with the same converter (see `OrderWorkflowTests.JsonOptions`) — `HttpContent.ReadFromJsonAsync`/`PostAsJsonAsync` use the .NET default options otherwise and will throw trying to parse a string into an enum.
- `OrderDetailDto.StatusHistory`/`CallAttempts` are populated **only** by `GetByIdAsync` (the admin single-order endpoint) — `CreateAsync`/`TrackAsync` (guest-facing) always return empty lists, deliberately, since `Reason`/call notes can contain internal admin context not meant for a guest. `ToDetailDto(order, includeHistory: false)` is the default; `ChangeStatusAsync`'s query now also `.Include(o => o.StatusHistory).Include(o => o.CallAttempts)` so the response reflects the just-added transition immediately (EF Core relationship fixup appends the newly-tracked entity to the already-loaded collection) without a second round trip.
- `Ecommerce.Application.Orders.IOrderCallAttemptService` / `Ecommerce.Infrastructure.Orders.OrderCallAttemptService` — the confirmation-center call log (CLAUDE.md section 13). `RecordAsync` enforces the order is currently `PendingConfirmation`/`CustomerUnreachable` (409 otherwise), computes `AttemptNumber` from the existing count, saves the `OrderCallAttempt`, then **delegates** to `IOrderService.ChangeStatusAsync` for `Confirmed`/`Cancelled` results (reusing the single `AllowedTransitions` source of truth rather than duplicating transition logic) — `NoAnswer`/`CallbackScheduled` just record the attempt and leave the order status untouched (an agent explicitly uses the existing "Marquer injoignable" status action for that, keeping "log a call" and "change status" as two separate, composable actions). `POST /api/orders/{id}/call-attempts`, same `OrderManagers` role as other order admin endpoints.
- `Order.DiscountTotal` + `Order.AppliedPromotions` (`OrderPromotion` audit rows — `PromotionId` nullable/no-FK, `PromotionName` **snapshotted**, `DiscountAmount` — same survive-catalog-changes rationale as `OrderItem`). Populated by `OrderService.CalculatePromotionsAsync`, called from `CreateAsync` right after `Order.Subtotal` is computed. Unlike `StatusHistory`/`CallAttempts`, `AppliedPromotions` and `DiscountTotal` are **always** included in `OrderDetailDto` (not gated behind an `includeHistory`-style flag) — a customer needs to see their own discount on the confirmation/tracking page, unlike internal admin audit trails.
- `Order` also carries 9 nullable marketing-attribution columns (`UtmSource`/`UtmMedium`/`UtmCampaign`/`UtmContent`/`UtmTerm`/`Fbclid`/`Ttclid`/`Referrer`/`LandingPage`, see Marketing namespace note below) — set once at `CreateAsync` from `CreateOrderRequest.MarketingAttribution`, never updated after. `OrderService.ToMarketingAttributionDto` returns `null` for the whole `OrderDetailDto.MarketingAttribution` field only if **all 9** are null, so a partial capture (e.g. just `landingPage`, no UTM params — a "Direct" visit) still surfaces as a non-null DTO with individually-null sub-fields, not a missing object.

Promotions namespaces worth knowing (CLAUDE.md section 20):
- `Ecommerce.Domain.Promotions` — `Promotion` (one entity covering all 8 CLAUDE.md `PromotionType` values: ProductDiscount/CategoryDiscount/FlashSale/PercentageDiscount/FixedAmountDiscount/BuyXGetY/FreeShipping/Coupon — see Important Decisions for why one entity instead of a type hierarchy), `PromotionProduct`/`PromotionCategory` (many-to-many join entities, real FK `Cascade` to `Product`/`Category` — unlike `OrderItem`/`OrderCallAttempt`, these are live scoping data, not audit history, so they're allowed to cascade-delete)
- `Ecommerce.Application.Promotions.IPromotionService` / `Ecommerce.Infrastructure.Promotions.PromotionService` — CRUD (`CreateAsync`/`UpdateAsync`/`GetByIdAsync`/`GetPagedAsync`) plus `GetActiveAsync` (public, non-coupon, currently in-window promotions, for storefront display). Product/category associations are replaced wholesale on every `UpdateAsync` (clear both collections, re-add from the request) rather than diffed — simple and correct for the expected list sizes.
- `OrderService.CalculatePromotionsAsync` (private, in `Ecommerce.Infrastructure.Orders.OrderService`) is where checkout-time discount calculation actually happens: loads active/in-window non-coupon promotions scoped to the cart's products/categories (or storewide, i.e. no products/categories attached), picks the **single highest-`Priority`** applicable promotion **per line item** (no stacking between automatic promotions — see Important Decisions), computes its discount via `ComputeItemDiscount` (which dispatches to `ComputeBuyXGetYDiscount` for `BuyXGetY` promotions — quantity-bundle math, see below — or `ComputeDiscount`, percentage/fixed-of-line-total, for every other type), then separately resolves an optional `CouponCode` from the request (a `Coupon`-type promotion looked up by exact code match) and applies it **on top of** whatever automatic discount already applied (coupons and automatic promotions do stack with each other, just not with other automatic promotions). An invalid/expired coupon code throws `ValidationAppException` (`400`), rejecting the whole order — a customer who typed a bad code should be told, not silently ignored. `FreeShipping` promotions zero `Order.ShippingCost` if matched (currently a no-op in practice since `ShippingCost` is always 0 anyway — see Important Decisions #21).
- `ComputeBuyXGetYDiscount` — "Buy X, Get Y" is evaluated **per line item only** (no combining partial quantities across different variants/products into one bundle): `bundleSize = BuyQuantity + GetQuantity`, `completeBundles = item.Quantity / bundleSize` (integer division — a partial/incomplete bundle earns nothing), `freeUnits = completeBundles * GetQuantity`, discount = `freeUnits * item.UnitPrice` (the free units are 100% off, not partially discounted). E.g. "Buy 2 Get 1" needs 3+ units of the *same* variant in one line; buying 1 of variant A + 2 of variant B does not combine into a bundle.
- `Ecommerce.Domain.Identity.Roles.PromotionManagers` — `SUPER_ADMIN,ADMIN,MARKETING_MANAGER` for `[Authorize(Roles = ...)]` on promotion admin endpoints.

Shipping namespaces worth knowing (CLAUDE.md sections 15–19):
- `Ecommerce.Domain.Shipping` — `Shipment` (one per `Order`, 1:1 via a unique index on `OrderId`), `ShipmentTrackingEvent` (audit history, mirrors `OrderStatusHistory`'s pattern), `ShippingCarrier` enum (Fake/Yalidine/ZRExpress), `NormalizedShippingStatus` enum (Created/PickedUp/InTransit/AtDestination/OutForDelivery/Delivered/Failed/Refused/Returned/Cancelled/Unknown — matches CLAUDE.md section 18's list exactly). Both the raw carrier status string (`ProviderStatus`) and the normalized enum are stored on every `Shipment`/`ShipmentTrackingEvent` row, per CLAUDE.md section 18's explicit instruction to keep both.
- `Ecommerce.Application.Shipping.IShippingProvider` — the CLAUDE.md section 15 abstraction: `Carrier`, `IsConfigured`, `CreateShipmentAsync`, `GetTrackingAsync`. Three implementations registered in DI simultaneously (resolved as `IEnumerable<IShippingProvider>`, keyed by `.Carrier` in `ShippingService`): `FakeShippingProvider` (Infrastructure, **fully functional**, Singleton so its in-memory per-shipment progress dictionary survives across requests — CLAUDE.md section 15 mandates this dev/test double), `YalidineShippingProvider` and `ZRExpressShippingProvider` (structural adapters only — every method throws `NotConfiguredAppException` unconditionally, since no real API documentation was available for either carrier and CLAUDE.md sections 16/17 explicitly forbid inventing endpoints/auth; `IsConfigured` is hardcoded `false` on both regardless of whether credentials are set, because credentials alone don't make an unimplemented integration usable — see Important Decisions).
- `Ecommerce.Application.Shipping.IShippingService` / `Ecommerce.Infrastructure.Shipping.ShippingService` — `CreateShipmentAsync` requires the order to be `ReadyToShip` (409 otherwise) and have no existing `Shipment` (409 otherwise), calls the selected provider, persists the `Shipment` + first `ShipmentTrackingEvent`, then **delegates** to `IOrderService.ChangeStatusAsync` to move the order `ReadyToShip → Shipped` (same transitions map as everywhere else, not duplicated). `SyncTrackingAsync` re-queries the provider, appends a new tracking event only if the status actually changed, and — via a `NormalizedShippingStatus → OrderStatus` lookup table — also drives the order's own status forward (`OutForDelivery`/`Delivered`/`DeliveryFailed`/`Refused`/`Returned`/`Cancelled`) through the same `ChangeStatusAsync` call; a `ConflictAppException` from an already-invalid transition (e.g. an admin manually moved the order in the meantime) is caught and swallowed so a sync never crashes, the tracking event is still recorded regardless. `GetLabelAsync` only works for `Fake` shipments (a clearly-marked placeholder text response) — any other carrier throws `NotConfiguredAppException`.
- `Ecommerce.Infrastructure.Shipping.ShippingSyncBackgroundService` (`BackgroundService`) — CLAUDE.md section 19's background sync (no carrier here supports webhooks). Polls every `ShippingSync:IntervalSeconds` (default 300s — "not aggressive", per spec) for shipments not yet in a terminal `NormalizedStatus`, calling `SyncTrackingAsync` on each inside its own DI scope; a single shipment's sync failure is logged and skipped, never aborts the whole cycle. Gated by `ShippingSync:Enabled` (defaults `true`; explicitly set to `false` in `AuthWebApplicationFactory`'s test config so it never runs during `dotnet test`).
- `Order.Shipment` (nullable nav, 1:1) is embedded directly into `OrderDetailDto.Shipment` — same reasoning as `AppliedPromotions`/`CallAttempts`: `OrderDetailDto` is the one place an admin (or, for tracking visibility, a guest) looks to see everything about an order, so `OrderService` reads the `Shipments` table directly (`.Include(o => o.Shipment).ThenInclude(s => s.TrackingEvents)`) rather than making the frontend fetch shipment info from a second endpoint. `ShippingService` itself never calls back into `IOrderService` to *read* order data, only to *change* its status — keeping the dependency direction one-way (Shipping → Orders, never the reverse for writes).
- `Ecommerce.Application.Common.Exceptions.NotConfiguredAppException` — new `AppException` subclass, `NOT_CONFIGURED` code, HTTP `501 Not Implemented`. Used whenever a provider genuinely cannot do what was asked (Yalidine/ZR Express calls, or a label request for a non-Fake carrier) — distinct from `ConflictAppException` (409, business-state conflicts) and `ValidationAppException` (400, bad input).

Marketing namespaces worth knowing (CLAUDE.md section 21):
- No `MarketingEvent`/attribution table exists — attribution is 9 nullable columns directly on `Order` (see Orders namespace note above), and the funnel events CLAUDE.md lists (`PAGE_VIEW`/`VIEW_CONTENT`/`ADD_TO_CART`/`INITIATE_CHECKOUT`/`ORDER_CREATED`) are fired **client-side only**, straight to whichever pixel is configured — nothing is logged server-side per-event. See Important Decisions for why (no real Meta/TikTok Conversions API credentials, same non-invented-integration principle as Yalidine/ZR Express).
- `Ecommerce.Application.Marketing.IMarketingService` / `Ecommerce.Infrastructure.Marketing.MarketingService` — one method, `GetSourceSummaryAsync(days)`: groups `Order`s created in the last N days by `UtmSource` (null bucketed as `"Direct"`), returning order count + summed `Total` per source. **Gotcha hit while building this**: projecting a `GroupBy` aggregate straight into a custom record's constructor (`.Select(g => new MarketingSourceSummaryDto(g.Key ?? "Direct", g.Count(), g.Sum(...)))`) fails at runtime with `InvalidOperationException: could not be translated` — EF Core/Npgsql can't turn that into SQL. Fix: project into an anonymous type first (`.Select(g => new { Source = g.Key, ... })`), materialize with `ToListAsync`, *then* map to the DTO record client-side. Apply this pattern to any future `GroupBy` that needs to land in a non-anonymous projection type.
- `Ecommerce.Domain.Identity.Roles.MarketingManagers` — `SUPER_ADMIN,ADMIN,MARKETING_MANAGER` (same role set as `PromotionManagers`, named separately per-feature for clarity) for `[Authorize(Roles = ...)]` on `GET /api/marketing/sources`.
- Frontend `lib/marketing/attribution.ts` — `captureAttributionOnLoad()` reads `utm_source`/`utm_medium`/`utm_campaign`/`utm_content`/`utm_term`/`fbclid`/`ttclid` from the URL plus `document.referrer`, and **always** records `landingPage` (`window.location.href`), into `sessionStorage` under `luna-marketing-attribution` — but only once per session (first-touch: a later page view with different/no UTM params never overwrites an already-captured attribution). `getStoredAttribution()` reads it back for `CheckoutPage` to include in `CreateOrderRequest.marketingAttribution`. Because `landingPage` is always set, a fully "Direct" visit (no UTM/referrer) still produces a stored attribution object — it just has `utmSource: undefined`, so the backend still buckets it as `"Direct"` correctly; a **truly** `null` `OrderDetailDto.marketingAttribution` only happens when the request omits the field entirely (e.g. a raw API call, not the storefront UI).
- Frontend `lib/marketing/pixels.ts` — `initPixels()` injects the Meta Pixel (`fbq`) / TikTok Pixel (`ttq`) loader scripts **only if** `VITE_META_PIXEL_ID`/`VITE_TIKTOK_PIXEL_ID` are set; with no ID, it's a silent no-op (no script tag, no `window.fbq`) — same "don't inject/fake an integration you can't actually run" principle as the shipping adapters. `trackEvent(name, params)` maps CLAUDE.md's 5 canonical event names to each pixel's own standard event names (e.g. `ORDER_CREATED` → Meta `Purchase` / TikTok `PlaceAnOrder`) and no-ops safely if the corresponding `window.fbq`/`window.ttq` isn't defined.

`types.ts` is hand-written, not generated from the backend — if a backend DTO shape changes, this file must be updated manually (no codegen pipeline exists yet). `lib/orders/transitions.ts` and `lib/format/slug.ts` have the same hand-sync risk, called out explicitly in their own file comments.

**Admin forms using `z.coerce.number()` need the 3-generic `useForm<TInput, TContext, TOutput>` pattern**, not `useForm<z.infer<typeof schema>>`: `zodResolver` coerces string→number during validation, so the DOM-facing input type (`z.input<typeof schema>`, where numeric fields are effectively `unknown`/`string`) and the post-validation output type (`z.output<typeof schema>`, where they're `number`) genuinely differ, and a single generic can't represent both — TypeScript will reject the resolver with a confusing "Types of parameters 'options' are incompatible" error otherwise. See `CategoryQuickManager.tsx`/`CreateProductForm.tsx` for the working pattern (`useForm<Input, unknown, Output>`); apply the same pattern to any future admin form with a numeric field.

## Implemented Features

Yalidine and ZR Express are structural-only (see Shipping bullet below — real integration blocked on API docs/credentials that don't exist); server-side Meta/TikTok Conversions API calls are similarly out of scope for the same reason. Auth, Products/Categories/Inventory, COD Orders, confirmation-center, Promotions, Shipping (Fake provider), and now Marketing attribution/pixels exist (see below). No server-side Cart — checkout is a single-step guest submission (see Important Decisions).

What IS implemented:
- Monorepo structure (`backend/`, `frontend/`)
- Backend solution builds and runs; Swagger UI available at `/swagger` in Development
- `AppDbContext` (IdentityDbContext, Guid keys) with custom table names (Users, Roles, UserRoles, RefreshTokens, etc.)
- **Authentication**: JWT login/refresh/logout/me. `POST /api/auth/login`, `POST /api/auth/refresh` (rotates the refresh token), `POST /api/auth/logout` (revokes it), `GET /api/auth/me` (`[Authorize]`, reads claims). Refresh tokens are opaque random strings, stored **hashed** (SHA-256) server-side, with rotation (old token revoked + linked to its replacement on every refresh).
- `IdentitySeeder` seeds the 7 roles from `Ecommerce.Domain.Identity.Roles` and an optional bootstrap `SUPER_ADMIN` user from the `InitialAdmin` config section, idempotently, on every startup where `ApplyMigrationsOnStartup=true`.
- Standardized API error responses (`{ success: false, error: { code, message } }`) for both application-level exceptions (`AppException` subclasses) and FluentValidation failures, via global exception-handling middleware.
- `Ecommerce.Domain.Identity.Roles` constants matching CLAUDE.md section 25 (SUPER_ADMIN, ADMIN, ORDER_MANAGER, CONFIRMATION_AGENT, STOCK_MANAGER, MARKETING_MANAGER, VIEWER) — now seeded into the database.
- `GET /health` (Npgsql connectivity check) and `GET /api/system/ping` (no-dependency smoke endpoint)
- EF Core migrations `InitialIdentity` and `AddRefreshTokens`
- CORS configured via `Cors:AllowedOrigins` config (env var `Cors__AllowedOrigins__0` in docker-compose)
- Admin route shell (`/admin/*`) with separate layout/navigation, now with a **working login + protected routes** (see the Orders/Products admin bullets below) — promotions/customers/shipping/marketing/users/settings pages remain `PagePlaceholder`.

## Database

PostgreSQL via Npgsql.EntityFrameworkCore.PostgreSQL 9.0.4.

Entities that currently exist (Identity only, via `AppDbContext : IdentityDbContext<ApplicationUser, ApplicationRole, Guid>`):
- `ApplicationUser` (`Users` table) — extends `IdentityUser<Guid>` with `FirstName`, `LastName`, `IsActive`, `CreatedAtUtc`

- `RefreshToken` (`RefreshTokens` table) — `UserId`, `TokenHash` (SHA-256, unique), `ExpiresAtUtc`, `RevokedAtUtc`, `ReplacedByTokenHash`; `IsActive` computed as not-revoked-and-not-expired

Catalog & Inventory entities (`Ecommerce.Domain.Catalog` / `Ecommerce.Domain.Inventory`):
- `Category` (`Categories` table) — `Name`, `Slug` (unique), `Description`, `IsActive`, `DisplayOrder`

- `ProductImage` (`ProductImages` table) — `ProductId` (FK, `Cascade`), `Url`, `AltText`, `DisplayOrder`, `IsPrimary`

- `Order` (`Orders` table) — `OrderNumber` (unique, `LUNA-YYMMDD-NNNN`), `Status` (string-converted enum), customer/delivery fields (`FirstName`/`LastName`/`Phone`/`Wilaya`/`Commune`/`Address`/`DeliveryType`/`Notes`), `PaymentMethod` (fixed `"COD"`), `PaymentStatus`, `Subtotal`/`ShippingCost`/`Total` (all numeric(10,2); `ShippingCost` is currently always 0 — no shipping-rate calculation yet), 9 nullable marketing-attribution columns (`UtmSource` indexed, `UtmMedium`/`UtmCampaign`/`UtmContent`/`UtmTerm` max 200 chars, `Fbclid`/`Ttclid` max 500, `Referrer`/`LandingPage` max 2000 — plain columns, not an EF owned type, matching the rest of `Order`'s flat shape)

- `OrderStatusHistory` (`OrderStatusHistories` table) — `OrderId` (FK `Cascade`), `OldStatus`/`NewStatus` (string-converted enums), `ChangedByUserId` (nullable Guid — null for system/guest-triggered creation), `Reason`

- `OrderPromotion` (`OrderPromotions` table) — `OrderId` (FK `Cascade`), `PromotionId` (nullable Guid, no FK — survives the promotion being edited/deleted later), `PromotionName` (**snapshotted**), `DiscountAmount` (numeric(10,2))

Promotion entities (`Ecommerce.Domain.Promotions`):
- `Promotion` (`Promotions` table) — `Name`, `Description`, `Type` (string-converted enum: ProductDiscount/CategoryDiscount/FlashSale/PercentageDiscount/FixedAmountDiscount/BuyXGetY/FreeShipping/Coupon), `PercentageValue` (nullable numeric(5,2)), `FixedAmountValue` (nullable numeric(10,2)), `BuyQuantity`/`GetQuantity` (nullable int, `BuyXGetY` only), `CouponCode` (nullable, unique via a partial index `WHERE "CouponCode" IS NOT NULL`), `StartsAtUtc`/`EndsAtUtc`, `IsActive`, `Priority` (int, higher wins when multiple promotions match the same line — see Important Decisions), plus an index on `(IsActive, StartsAtUtc, EndsAtUtc)` for the checkout-time active-window lookup

## API

Base URL (local/dev): `http://localhost:5000` (docker-compose maps container port 8080 → host `BACKEND_PORT`, default 5000).

Endpoints that exist today:
- `GET /health` — Npgsql-backed health check
- `GET /api/system/ping` — trivial liveness endpoint, no dependencies
- `GET /swagger` — Swagger UI (Development only)
- `POST /api/auth/login` — `{ email, password }` → `AuthResponse` (access token, refresh token, expiries, `CurrentUserResponse`). Generic `401 UNAUTHORIZED` for both unknown email and wrong password (no user enumeration).

- `POST /api/auth/logout` — `{ refreshToken }` → `204`; revokes the token (idempotent, no error if already revoked/unknown).
- `GET /api/auth/me` — `[Authorize]`, reads claims from the validated JWT, returns `CurrentUserResponse`.

Catalog (public reads, `CatalogManagers` role = SUPER_ADMIN/ADMIN/STOCK_MANAGER for writes):
- `GET /api/categories?includeInactive=` / `GET /api/categories/{slug}` — public; `POST /api/categories` / `PUT /api/categories/{id}` — admin
- `GET /api/products?category={slug}&page=&pageSize=&includeInactive=` (paged) / `GET /api/products/{slug}` (full detail incl. variants + live stock) — public; `POST /api/products` (with initial variants) / `PUT /api/products/{id}` / `POST /api/products/{id}/variants` — admin
- `GET /api/inventory/{variantId}` / `GET /api/inventory/{variantId}/transactions` / `POST /api/inventory/restock` / `POST /api/inventory/adjust` — admin only (whole controller is `[Authorize(Roles = Roles.CatalogManagers)]`)

Orders (guest checkout is public; admin endpoints need `OrderManagers` role = SUPER_ADMIN/ADMIN/ORDER_MANAGER/CONFIRMATION_AGENT):
- `POST /api/orders` — public, creates a COD order from `{ firstName, lastName, phone, wilaya, commune, address, deliveryType, notes?, items: [{ productVariantId, quantity }] }`. `409 CONFLICT` (not `400`) if any item is out of stock — the whole order fails atomically.
- `GET /api/orders/track?orderNumber=&phone=` — public, guest order lookup; `404` unless both match (no order-number enumeration).
- `GET /api/orders?status=&page=&pageSize=`, `GET /api/orders/{id}` — admin.
- `POST /api/orders/{id}/status` — admin, `{ newStatus, reason? }`. `409 CONFLICT` if the transition isn't in the allowed map for the order's current status.
- `POST /api/orders/{id}/call-attempts` — admin, `{ result, notes?, nextCallAt? }` (`result` one of `NoAnswer`/`Confirmed`/`Cancelled`/`CallbackScheduled`). `409 CONFLICT` if the order isn't `PendingConfirmation`/`CustomerUnreachable`; `400` if `CallbackScheduled` is missing a future `nextCallAt`. `Confirmed`/`Cancelled` also transition the order status (via the same logic as `POST .../status`); `NoAnswer`/`CallbackScheduled` only append to the call log.
- `POST /api/orders` also accepts an optional `couponCode` field now — `400 VALIDATION_ERROR` if it doesn't match an active, in-window `Coupon`-type promotion. `OrderDetailDto` (all order endpoints) gained `discountTotal` and `appliedPromotions: [{ id, promotionId, promotionName, discountAmount }]` — always populated (unlike `statusHistory`/`callAttempts`, which stay admin-only), since a customer needs to see their own discount.

Promotions (public active-list read; admin CRUD needs `PromotionManagers` role = SUPER_ADMIN/ADMIN/MARKETING_MANAGER):
- `GET /api/promotions/active` — public, currently-active/in-window, non-coupon promotions (storefront display; coupon codes are never listable, only redeemable by exact code).
- `GET /api/promotions?includeInactive=&page=&pageSize=`, `GET /api/promotions/{id}` — admin (list DTO omits the raw coupon code, exposing only `hasCouponCode: boolean`; detail DTO exposes the full code for editing).
- `POST /api/promotions`, `PUT /api/promotions/{id}` — admin, `{ name, description?, type, percentageValue?, fixedAmountValue?, buyQuantity?, getQuantity?, couponCode?, startsAtUtc, endsAtUtc, isActive, priority, productIds, categoryIds }`. Field requirements are conditional on `type` (e.g. `ProductDiscount` requires a non-empty `productIds`, `Coupon` requires exactly one of `percentageValue`/`fixedAmountValue`) — see `SavePromotionRequestValidator`.

Shipping (all admin, `OrderManagers` role):
- `POST /api/orders/{id}/shipment` — `{ carrier: "Fake" | "Yalidine" | "ZRExpress" }` → `ShipmentDto`. `409 CONFLICT` if the order isn't `ReadyToShip` or already has a shipment; `501 NOT_CONFIGURED` for Yalidine/ZR Express (not implemented — no real API docs available). Also transitions the order to `Shipped`.
- `POST /api/shipments/{id}/sync` — re-checks tracking with the provider, records a new event on change, and drives the order's status forward when the normalized status maps to one (`OutForDelivery`/`Delivered`/`DeliveryFailed`/`Refused`/`Returned`/`Cancelled`).
- `GET /api/shipments/{id}/label` — `text/plain`; only works for `Fake` shipments (clearly-marked placeholder), `501` otherwise.
- `GET /api/shipping/carriers` — `[{ carrier, isConfigured, unavailableReason }]`, for the admin carrier picker / `/admin/shipping` status page.
- `OrderDetailDto` gained `shipment: ShipmentDto | null` — always populated (like `appliedPromotions`), not admin-only.

Marketing (admin, new `MarketingManagers` role = SUPER_ADMIN/ADMIN/MARKETING_MANAGER):
- `GET /api/marketing/sources?days=` (default 30) — `[{ source, orderCount, totalRevenue }]`, orders grouped by `UtmSource` (`null` bucketed as `"Direct"`) over the window, ordered by `orderCount` descending.
- `POST /api/orders` also accepts an optional `marketingAttribution: { utmSource?, utmMedium?, utmCampaign?, utmContent?, utmTerm?, fbclid?, ttclid?, referrer?, landingPage? }` — all fields optional strings, no validation beyond what EF Core's column max-lengths enforce. `OrderDetailDto` gained `marketingAttribution` (same shape, all fields nullable) — always populated when present, `null` only if the request omitted the field/every sub-field was empty.

Errors follow `{ success: false, error: { code, message } }` (CLAUDE.md section 27) — codes seen so far: `UNAUTHORIZED`, `VALIDATION_ERROR`, `INTERNAL_ERROR`, `NOT_FOUND`, `CONFLICT`, `NOT_CONFIGURED` (`501`, new — provider genuinely can't do what was asked) (see `Ecommerce.Application.Common.Exceptions.AppException` for the full set).

## Known Issues

- Swashbuckle.AspNetCore 10.2.3 pulls in `Microsoft.OpenApi` 2.7.5, whose API (`Microsoft.OpenApi` namespace, `OpenApiSecuritySchemeReference`, factory-based `AddSecurityRequirement`) differs substantially from the older `Microsoft.OpenApi.Models` namespace used by most online examples/older Swashbuckle docs — if you copy JWT/Swagger setup snippets from older sources they will not compile as-is. See `Program.cs` for the working pattern.
- The ASP.NET Core built-in `Microsoft.AspNetCore.OpenApi` package (used for the default `AddOpenApi()`/`MapOpenApi()` minimal-API template code) must NOT be referenced alongside Swashbuckle — it pulls a conflicting `Microsoft.OpenApi` 1.x, which causes a `ReflectionTypeLoadException` at runtime when the app tries to build the controller list. This package reference was deliberately removed from `Ecommerce.Api.csproj`.
- `dotnet new sln` on this machine (SDK 10.0.301 is the resolved default) generates the new `.slnx` format, not `.sln`. The Dockerfile and any tooling must reference `Ecommerce.slnx`.
- The dev-only auto-migration on backend startup is gated by the `ApplyMigrationsOnStartup` config key (env var `ApplyMigrationsOnStartup` / `ApplyMigrationsOnStartup=true` in docker-compose), deliberately NOT tied to `ASPNETCORE_ENVIRONMENT=Development`, because `WebApplicationFactory` in tests also runs in the Development environment and would otherwise try to migrate a non-existent test database on every test run.
- `appsettings.Development.json` contains a **dev-only** dummy Postgres password and JWT signing key (clearly non-production values) so `dotnet run` works out of the box against a locally-running Postgres without Docker. These must never be reused in staging/production — real secrets must come from environment variables / secret management per CLAUDE.md section 24.
- **This dev machine has a native Windows PostgreSQL service already running on port 5432** (`postgres.exe`, Windows service, unrelated to this project). It does NOT block `docker compose`'s own `postgres` container from also publishing to host port 5432 (empirically verified working), but it DOES mean: (a) `appsettings.Development.json`'s `luna`/`luna_dev_password` credentials will hit whichever Postgres instance is currently bound to 5432 and fail auth if it's the native one and not the intended one — if `dotnet run` (non-Docker) can't connect, check `netstat -ano | grep 5432` / `tasklist` first; (b) this is exactly what caused the bug described below to surface. If this becomes a recurring problem, consider changing the local dev Postgres port in `appsettings.Development.json` and `docker-compose.yml`.
- **(Fixed, but worth knowing)** `AddInfrastructure`, the health check registration, and the original JWT bearer setup all read `IConfiguration` **eagerly** — evaluating `configuration.GetConnectionString(...)` / `configuration.GetSection(...).Get<T>()` into a local variable at service-registration time, before `WebApplicationBuilder.Build()`. Any configuration source composed later (in tests: `WebApplicationFactory`'s `ConfigureAppConfiguration` overrides) was silently ignored, and the app fell back to whatever `appsettings.{Environment}.json` already had — which, combined with the native Postgres above, produced a confusing `password authentication failed for user "luna"` error instead of an obvious "wrong config" signal. **Rule of thumb going forward: never read `IConfiguration` into a local variable outside of a `Configure<T>`/`AddOptions<T>`/`(IServiceProvider, options) =>` callback in `Program.cs` or `AddInfrastructure`** — always resolve it lazily via DI so both tests and any future runtime config changes are respected.
- **Playwright browser-test gotcha (not an app bug, but bit us once):** a `page.waitForFunction` checking `element.textContent.includes('9')` to detect a stock value of `9` resolved instantly and spuriously because the test's own SKU string (`SKU-92971551`) happens to contain the digit `9` — the screenshot taken right after showed the *old* stock value, making it look like the UI hadn't updated when in fact the backend mutation had already succeeded (confirmed via a direct API call). When writing Playwright assertions against numeric UI values, match on a delimited/exact pattern (e.g. a regex with word boundaries, or a dedicated `data-testid`/`aria-label`) rather than a bare substring check, especially near SKUs or IDs that are themselves numeric-looking strings.
- **Playwright/Chromium gotcha #2:** `document.body.innerText` (and any element's `.innerText`) reflects **rendered** text, including CSS `text-transform` — a heading styled with Tailwind's `uppercase` class reads back through `innerText` as literal uppercase (e.g. a DOM/JSX string `"Journal d'appels"` comes back as `"JOURNAL D'APPELS"`). A case-sensitive `.includes(...)` check against `innerText` will silently never match text under an `uppercase`/`capitalize`/`lowercase` ancestor. Playwright's own `text=` selector engine is case-insensitive by default so this doesn't bite selector-based waits, only raw `innerText` string checks in `page.evaluate`/`waitForFunction` — lowercase both sides when comparing, or use `.textContent` (unaffected by CSS) instead of `.innerText` if the literal DOM string is what you actually want.
- **Playwright test-script gotcha #3 (same family as #1 — "the test's own data made the assertion pass early", not an app bug):** a `page.waitForFunction` checking whether a just-created promotion's name appeared anywhere on `/admin/promotions` resolved **instantly**, before the `POST /api/promotions` request had even completed, because a promotion with the exact same literal name (`"Promo Robe -20%"`) already existed on the page from an earlier, uncleaned test run reusing the same hardcoded name. The premature resolution let the script fire a guest checkout request before the new promotion was actually persisted, producing an apparently-missing discount that looked exactly like an app bug (confirmed via direct `curl` against the same live database that the *real* promotion, scoped correctly, active, in-window, applied perfectly). **Rule of thumb: when a Playwright script asserts on a UI mutation's result and the test reuses literal names/values across runs (no per-run uniqueness or cleanup), don't wait for text to merely appear — wait for the actual network response** (`page.waitForResponse` racing against the triggering `page.click`, or a per-run-unique name) — a stale "it's already there from last time" false positive is easy to miss since the *rest* of the assertion chain looks like a real failure downstream.
- **EF Core / Npgsql query-translation gotcha:** `.GroupBy(...).Select(g => new SomeRecord(g.Key, g.Count(), g.Sum(...)))` — projecting a `GroupBy` aggregate straight into a **custom record's constructor** — fails at runtime with `InvalidOperationException: ... could not be translated`, even though the exact same shape as an **anonymous type** (`new { Source = g.Key, ... }`) translates fine. Hit this building `MarketingService.GetSourceSummaryAsync`. Fix: project into an anonymous type, `ToListAsync()` to materialize, *then* map to the target record client-side in a second `.Select(...).ToList()`. Apply this pattern to any future `GroupBy`-with-aggregates query that needs to land in a non-anonymous type.
- **Playwright test-script false-assumption (not an app bug, but a genuinely wrong test expectation, not just a timing race like gotchas #1/#3):** a marketing-verification test asserted that landing on the storefront with zero UTM params captures *no* attribution in `sessionStorage` at all — but `captureAttributionOnLoad()` deliberately **always** records `landingPage` (`window.location.href`) as baseline context, even for a fully "Direct" visit with no campaign markers. So `sessionStorage` is never actually empty after a landing; the correct check is whether `utmSource` specifically stayed unset (which is what makes the backend bucket the eventual order as `"Direct"`), not whether the whole attribution object is absent. Fixed the test assertion, not the app — the always-capture-landingPage behavior is intentional (see Important Decisions).

## Important Decisions

1. The project is a custom e-commerce platform and must not depend on Shopify or WooCommerce.
2. COD is the primary payment method.
3. ~~Inventory is managed at product-variant level (not yet built).~~ Built: one `InventoryRecord` per `ProductVariant`, never at `Product` level.
4. ~~Shipping providers are accessed through `IShippingProvider` (not yet built).~~ Built: `IShippingProvider` + `FakeShippingProvider`/`YalidineShippingProvider`/`ZRExpressShippingProvider`, orchestrated by `ShippingService`.
5. Mobile-first design is mandatory (Tailwind v4 chosen partly for its low-overhead setup; no desktop-first patterns introduced).
6. The backend is the source of truth for business logic.
7. `PROJECT_CONTEXT.md` (this file, at the repo root, exact filename) is the persistent project memory — supersedes the earlier draft `Project Context.md`, which has been removed to avoid two diverging copies.
8. Identity uses `Guid` keys and custom table names (`Users`, `Roles`, ...) instead of the AspNet* defaults, decided at bootstrap time to keep the schema clean from the start — changing this later would require a destructive migration.
9. `dotnet-ef` is pinned as a local tool at 9.0.19 (matching the EF Core package version) rather than relying on the machine's global tool, to avoid SDK-version drift breaking migrations for other contributors.
10. Auto-migration on backend startup is opt-in via `ApplyMigrationsOnStartup`, not automatic in Development, specifically to keep the test suite (which runs in the Development environment) independent of a live database.
11. Refresh tokens are opaque random strings stored **hashed** (SHA-256) server-side, never plaintext — same rationale as password hashing. Rotation on every refresh (old token revoked and linked to its replacement) so token reuse after refresh is detectable/rejected.
12. No public self-registration endpoint. Guest checkout means customers never need accounts (CLAUDE.md section 11); staff/admin accounts (the only users of this Identity system so far) are provisioned via the `InitialAdmin` bootstrap seed for now. A proper admin-side user-management endpoint is deferred to the `/admin/users` feature (CLAUDE.md section 22/23), not built as part of core auth.
13. All `IConfiguration` reads in service-registration code must be lazy (resolved via DI at first use), never eager local-variable reads — see Known Issues for the bug this caused and the fix pattern to follow for all future config-dependent registrations (`AddDbContext`, health checks, options binding, etc.).
14. Overselling is prevented at the database-query level, not in application code: every `InventoryService` stock mutation is a single `ExecuteUpdateAsync` call whose `Where` clause encodes the invariant (e.g. `AvailableQuantity >= quantity`) so the guard and the write happen atomically in one SQL statement. Loading the entity, checking a condition in C#, then calling `SaveChangesAsync` would have a race window under concurrent requests — deliberately avoided.
15. `InventoryTransaction.Quantity` is always a positive magnitude for Reserve/Release/Sale/Return/Restock (the bucket transition is implied by `Type`), but can be **negative** for Adjustment (a manual correction can go either direction) — this is the one type where the sign is meaningful and must be preserved for the audit trail.
16. `Reserve`/`Release`/`RecordSale`/`RecordReturn` on `IInventoryService` are implemented and unit/integration-tested now, but intentionally have no HTTP endpoint yet — there is no real caller (Cart/Order) for them yet, and CLAUDE.md section 44 discourages building unused public API surface. They're ready for the Order feature to call directly.
17. Product `Slug` and `ProductVariant` `Sku` are supplied by the admin/caller (validated via a shared regex rule), not auto-generated from the name — kept simple for this pass; revisit if UX feedback asks for auto-slugging.
18. **No server-side Cart/CartItem entity.** Since guest checkout is mandatory and there are no customer accounts (CLAUDE.md section 11), there is no logged-in customer to sync a cart across devices for — persisting it server-side would add a full CRUD surface for zero real benefit right now. The frontend cart lives in browser state (e.g. localStorage) and is submitted as a flat `items: [{ productVariantId, quantity }]` list directly to `POST /api/orders` at checkout. Revisit only if a real requirement emerges (e.g. cart abandonment recovery emails).
19. ~~`OrderCallAttempt` / confirmation-center workflow (CLAUDE.md section 13) is deliberately deferred.~~ Built: `OrderCallAttempt` entity + `POST /api/orders/{id}/call-attempts` + real `/admin/orders/confirmation` queue UI, now that the admin order UI exists to consume it.
20. Order status transitions are enforced via a hardcoded `Dictionary<OrderStatus, OrderStatus[]>` in `OrderService`, not a database-driven workflow engine — intentionally simple and exhaustive (12 states, ~20 edges), matches CLAUDE.md's explicit list of states, and is trivial to unit-test. Revisit only if the workflow needs to become configurable per-tenant or per-carrier.
21. `Order.ShippingCost` is hardcoded to 0 — still true even after the `IShippingProvider` abstraction was built (Important Decision #4), because no provider (including Fake) implements a *rate lookup*; `IShippingProvider` only covers shipment creation and tracking, not pricing (CLAUDE.md sections 15–19 don't mention a rates capability being required for this pass). `Order.Total` will need recalculating once shipping-rate calculation is added; this is a known gap, not an oversight.
22. `OrderItem.ProductVariantId` has no FK constraint to `ProductVariants` (unlike `InventoryTransaction`, which does). Order history must remain intact and queryable even if a product/variant is later deleted from the catalog — the snapshot fields (`ProductName`, `Sku`, etc.) are what matters for a placed order, not a live join to the catalog.
23. Frontend `types.ts` DTOs are hand-written, not generated from the backend (no OpenAPI-codegen pipeline set up). Acceptable at the current size; revisit if the two start drifting often.
24. `OrderConfirmationPage` reads the just-created order from React Router navigation `state`, not a fresh API call — it doesn't have the customer's phone number handy to call the (phone-verified) track endpoint, and re-fetching without that verification would defeat the anti-enumeration protection on `GET /api/orders/track`. On a page reload (state lost), it shows a fallback pointing to `/track-order` instead of silently failing.
25. `apiClient` has no auth-token attachment yet — deliberately, since every endpoint the storefront currently calls is public (categories, products, order create/track). This will need to be added when the admin UI (which needs `Authorization: Bearer`) is built, not before.
26. `lib/orders/transitions.ts` (frontend `ALLOWED_TRANSITIONS`) duplicates the backend's `OrderService.AllowedTransitions` by hand rather than fetching it from an endpoint. The backend is still the enforcement point (any mismatch just means the UI briefly offers a button that the API then rejects with `409`) — a dedicated "valid transitions for order X" endpoint would remove this duplication but wasn't worth building for a 12-entry map; revisit if the state machine grows or changes frequently.
27. Admin status-change reasons are collected via a plain `window.prompt()`, not a custom modal component — deliberately minimal for an internal tool; only prompts when the target status is one where CLAUDE.md's audit trail intent (section 14) makes a reason meaningful (Cancelled/CustomerUnreachable/DeliveryFailed/Refused/Returned), not for every transition.
28. `OrderDetailDto.StatusHistory` is empty for guest-facing responses (`CreateAsync`/`TrackAsync`) and populated only for the admin `GetByIdAsync`/`ChangeStatusAsync` responses — see the Orders namespace note in Current Architecture. This is a deliberate data-exposure boundary, not an oversight: transition `Reason` text may contain internal notes not meant for customers.
29. Admin dashboard shows only real, currently-computable numbers (total orders + counts per key status, via the existing paged endpoint read `pageSize=1` for cheap `totalCount`s) — explicitly no revenue/analytics figures, since CLAUDE.md section 42 ("No Fake Success") extends in spirit to not fabricating business metrics the backend can't yet produce. A real dashboard aggregation endpoint is future work, not something to fake client-side.
30. `includeInactive` on the product/category list endpoints is a plain query param on the existing `[AllowAnonymous]` GET endpoints, not a separate admin-only route. Deliberate: it's not sensitive data (worst case, a guest sees a discontinued product isn't for sale), and adding a parallel admin endpoint just to gate a boolean would be the kind of unnecessary surface CLAUDE.md section 44 warns against.
31. No separate `/admin/inventory` page. Stock actions (restock/adjust) live inline on `/admin/products`, inside each product's expandable variant panel, because that's the same data an admin is already looking at when managing a product — a separate page would just mean re-fetching and re-displaying the same variants elsewhere. The `/admin/inventory` route still exists in the router (renders `PagePlaceholder`) since it's part of the original CLAUDE.md nav structure, but isn't the primary way to manage stock.
32. Admin catalog forms (`CategoryQuickManager`, `CreateProductForm`) use `useForm<Input, unknown, Output>` (react-hook-form's 3-generic form) instead of the simpler `useForm<z.infer<typeof schema>>` — required because `z.coerce.number()` fields make the Zod schema's input and output types genuinely different, and `zodResolver` needs both. Documented in Current Architecture; apply the same pattern to future forms with numeric fields rather than reintroducing the type error.
33. `ProductVariantsPanel` fetches full product detail (`GET /api/products/{slug}`) on demand when a product row is expanded, rather than the product list endpoint returning variants inline — keeps the list endpoint lightweight (it's also the public storefront listing endpoint) and matches the existing `ProductDetailDto` shape the storefront's `ProductPage` already uses, so no new DTO was needed.
34. `OrderCallAttemptService.RecordAsync` only auto-changes order status for `Confirmed`/`Cancelled` results, not `NoAnswer` (and `CallbackScheduled` doesn't have an obvious target status either). A `NoAnswer` call is just evidence toward the agent's own decision to mark the order `CustomerUnreachable` via the existing status-action button — conflating "log this call" with "change the order status" into one implicit side effect would make the confirmation-center UI's two actions (call form vs. status buttons) unpredictable about which one actually moves the order. Revisit only if agents report the two-step flow (log NoAnswer, then separately click "Marquer injoignable") is real friction in practice.
35. `/admin/orders/confirmation` issues two separate `getPaged` calls (one per status) rather than a single request, because the backend's `GET /api/orders` filter only accepts one `status` value — building a multi-status filter endpoint just for this one page wasn't worth it yet (CLAUDE.md section 44); revisit if more multi-status admin views are needed.
36. `Promotion` is **one entity** covering all 8 CLAUDE.md `PromotionType` values, not a type hierarchy or 8 separate tables. CLAUDE.md's list conflates genuinely orthogonal concerns (discount *mechanic*: percentage/fixed/BuyXGetY/free-shipping; *scope*: product/category/storewide; *activation*: automatic/coupon) into one flat enum — rather than inventing an abstraction CLAUDE.md doesn't ask for, one entity with nullable fields relevant-per-type (validated conditionally by `SavePromotionRequestValidator`) matches the letter of the spec exactly and is far simpler to query/administer. Revisit only if a `Type` combination is needed that this flat model can't express (e.g. a coupon that's ALSO product-scoped AND percentage-off — currently coupons apply storewide or to their own product/category scope using the same `Products`/`Categories` collections as any other type, so this is actually already supported).
37. Automatic (non-coupon) promotions **do not stack with each other** — only the single highest-`Priority` match applies per line item. Coupon codes, however, **do stack on top of** whatever automatic discount already applied. This asymmetry is deliberate: merchants expect "best automatic deal wins" (predictable, no need to reason about combinatorial stacking rules across dozens of auto-promotions), but a coupon is an explicit, one-at-a-time customer action that should always do *something* additional or the code feels broken. Revisit if the business wants configurable stacking rules — not built, since CLAUDE.md doesn't specify stacking semantics and this is the simplest predictable default.
38. ~~`BuyXGetY` promotions can be created and stored via the admin UI but are excluded from checkout matching.~~ **Built**: `OrderService.CalculatePromotionsAsync` now includes `BuyXGetY` in candidate matching and dispatches its discount through `ComputeBuyXGetYDiscount` (per-line-item only, complete bundles only — see the `ComputeBuyXGetYDiscount` bullet in Current Architecture for the exact math). Cross-line/cross-variant bundle combining was deliberately not built — CLAUDE.md doesn't specify it, and the existing per-line promotion model doesn't support combining partial quantities across different variants/products; revisit only if the business needs "any 3 items from category X" style bundles instead of same-variant bundles.
39. `FreeShipping` promotions are fully wired (matched, and would zero `Order.ShippingCost` if matched) but have **no visible effect today** since `Order.ShippingCost` is hardcoded to `0` (Important Decision #21 — no `IShippingProvider` yet). Not a bug: the promotion type exists and will start working automatically once real shipping-cost calculation lands, no promotion-side changes needed then.
40. `OrderPromotion` rows are only recorded for **non-zero** discounts — a promotion that matched a cart but computed to a `0` discount (e.g. a `FreeShipping` promo when shipping is already `0`) doesn't get a meaningless `$0 "applied"` audit entry. Keeps `Order.AppliedPromotions` meaningful for both the customer-facing confirmation display and the admin audit view.
41. Coupon codes are validated **server-side only, at order-submission time** — the storefront checkout form has no live "apply coupon and preview the discount" step, since that would require a dedicated cart-pricing-preview endpoint that doesn't exist yet (and CLAUDE.md section 41 already means the client never computes/display authoritative prices anyway). The discount is shown for the first time on the order confirmation page, after the order is created. Revisit if cart-abandonment data suggests customers need to see the discount before committing to checkout.
42. `YalidineShippingProvider.IsConfigured`/`ZRExpressShippingProvider.IsConfigured` are **hardcoded `false`**, deliberately not derived from whether credentials are present (`YalidineOptions.IsConfigured`/`ZRExpressOptions.IsConfigured` still check that separately, for anyone who wants to know "have the env vars at least been set"). Credentials alone don't make an unimplemented HTTP integration usable — reporting `IsConfigured: true` just because `YALIDINE_API_TOKEN` is set would be a form of the "fake success" CLAUDE.md section 42 forbids, since the admin UI's carrier picker/`/admin/shipping` page would then claim a carrier is ready when every call still throws.
43. Creating a shipment requires the order to already be `ReadyToShip` (not `Confirmed` or `Preparing`) — matches the natural real-world sequence (pack the order, *then* hand it to a carrier) and means `ShippingService` only ever needs to make one transition (`ReadyToShip → Shipped`), which is always valid per the existing `AllowedTransitions` map, so shipment creation can never itself trigger a `409` from the order side.
44. `ShippingService.SyncTrackingAsync` catches and swallows `ConflictAppException` when driving the order status forward — if an admin has already manually moved the order to a state where the carrier's reported transition is no longer valid (e.g. manually cancelled), the sync still records the tracking event (carrier truth is always preserved) but doesn't crash or roll back; the order simply keeps its manually-set status. Silent-but-logged was chosen over surfacing an error, since this runs unattended from the background sync service most of the time and there's no user waiting on the response.
45. `FakeShippingProvider` is registered as a **Singleton** (every other application service in this codebase is Scoped) specifically so its in-memory `ConcurrentDictionary<string, int>` progress tracker survives across requests within the running process — without that, "advance one step per sync call" wouldn't work, since a fresh Scoped instance would have no memory of the shipment's prior progress. `YalidineShippingProvider`/`ZRExpressShippingProvider` stay Scoped like everything else since they hold no meaningful state (every call throws immediately).
46. No shipping-rate/cost calculation was added even though `IShippingProvider` now exists — CLAUDE.md sections 15–19 describe shipment creation, tracking, normalization, and sync, but never a rates capability, and `FakeShippingProvider` correctly has nothing real to quote a rate from. `Order.ShippingCost` staying at `0` (Important Decision #21) is intentionally unchanged by this pass; rate calculation is a distinct follow-up, not an oversight in this one.
47. Marketing attribution lives as **9 plain nullable columns directly on `Order`**, not a separate `MarketingAttribution`/owned-entity table — same rationale as the flat-column approach used everywhere else on `Order` (no existing precedent for EF Core owned types in this codebase, and it's always 1:1, write-once, never queried independently of an order except for the `UtmSource` aggregate in `MarketingService`, which works fine against a plain indexed column).
48. `captureAttributionOnLoad()` **always** records `landingPage` (and `referrer`, when present) into `sessionStorage`, even when zero UTM params/click-IDs are present — a "Direct" visit still gets baseline landing-page context captured. Only `utmSource` (and the other UTM/click-ID fields) staying unset is what makes `MarketingService.GetSourceSummaryAsync` bucket the resulting order as `"Direct"`; the presence of a stored attribution object is not itself a signal of a tracked visit. A Playwright test wrongly assumed "no UTM params → no stored attribution" and had to be corrected — see Known Issues.
49. Attribution capture is **first-touch, not last-touch**: `captureAttributionOnLoad()` only writes to `sessionStorage` if nothing is stored yet for the session, so the *first* ad click/campaign a visitor arrives from gets credit for an eventual order, even if they browse through several more pages (possibly via a different, unmarked link) before checking out. No configuration option for last-touch was built — CLAUDE.md doesn't specify a model, and first-touch is the simpler, more common default for small-catalog COD stores where the "closing" touch is usually just organic re-visits to a cart.
50. No backend `MarketingEvent` audit table was built for the 5 CLAUDE.md funnel events (`PAGE_VIEW`/`VIEW_CONTENT`/`ADD_TO_CART`/`INITIATE_CHECKOUT`/`ORDER_CREATED`) — they fire directly from the browser to whichever pixel (Meta/TikTok) is configured, exactly like a normal pixel integration works, and CLAUDE.md doesn't ask for a server-side copy of them. If server-side event logging is ever needed (e.g. for a future analytics dashboard independent of Meta/TikTok's own reporting), it should be a deliberate, separate addition — not assumed as part of "wire up the pixels."
51. Server-side Meta/TikTok Conversions API calls for post-purchase lifecycle events (`ORDER_CONFIRMED`/`ORDER_SHIPPED`/`ORDER_DELIVERED`/`ORDER_CANCELLED`) were **not implemented** — same non-invented-integration principle as Yalidine/ZR Express (Important Decisions #42): no real Meta/TikTok API credentials or app secrets exist in this project, and guessing at the Conversions API request shape/auth would risk silently failing or, worse, appearing to work while sending malformed events. Only `ORDER_CREATED` fires (client-side, from `CheckoutPage`, immediately after a successful order) since it's the one lifecycle moment where the customer is still on-page.

1. Shipping-rate calculation — now that `IShippingProvider`/`ShippingService` exist, a rates capability (even a flat/simulated one on `FakeShippingProvider`) would let `Order.ShippingCost` become non-zero, which would also make `FreeShipping` promotions visibly do something (Important Decision #39/#46).
